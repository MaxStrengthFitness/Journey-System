# The Oct 12 release

*Branch `oct12/release`, on master `5a0bf7ea` (live since Oct 11 2026), not
pushed. Four branches built overnight on Oct 11 to 12 2026, each reviewed,
attacked and gated on its own, merged into one branch and gated again. Ships
with ONE script, `scripts/ship/ship-oct12.ps1` (`-Stage prepare`, `-Stage
golive`, `-Stage seed`). The three ship scripts the branches brought
(`ship-staff-webhook.ps1`, `ship-sessions.ps1`, `ship-studio-map.ps1`) are
kept for the record and say at the top that this release replaces them.*

"counted once" markers whose session is gone.

**Why one release.** The studio map and the sessions round both change
`firestore.rules`, and Firestore holds one rules file: shipped apart, the
second deploy would drop the first one's rules (the map's would remove the
finish marker's path, and every new Finish would be refused its marker). So
the two had to be merged before either rules deploy, and the rules lint now
fails on any rules file without `match /finish/{docId}`. Once merged, one
release is also the cheapest for AJ: **one push, one Render deploy (the web
service and both crons), one rules deploy, one index deploy and one Cloud
Function**, with one restore point to go back to.

## 2. What changes for whom

**Trainers**
- My Studio → Machines opens on **the map** once the studio has one with a
  machine on it (List one tap away; a phone keeps the List). Tapping a machine
  anywhere (the map, Relay, the Catalog, Operations, Admins) opens the same
  card.
- Relay's floor opens in **Cleaning**: tap a machine when it's wiped, or Mark
  all. Everyone's marks show on every iPad, with no names. The "Wipe down every
  machine" card counts the real marks ("12 of 19 wiped today").
- **Finish** feels the same; very rarely it says "…was already finished on
  another iPad. It counts once." instead of counting twice.
- A trainer signed in on two devices sees **Continue on this iPad** on the
  other one.
- An unfinished session: **Resume or finish** on the client's profile, an
  **Open** row for open sessions on the Client Directory, and the Hub card says
  **Paused**, **At End Session** or **Left open**. Anyone at the studio can
  resume or finish a session left open there, and discard one (someone else's
  from the next studio day).
- Learning: two new Academy topics and a longer Research page.

**Leaders** (everything above, and)
- **Draw the floor / Arrange the floor**, remodel plans that may hold machines
  still to buy, **Sizes**, and Out of service on the machine's card.
- Operations → Today: **Not finished (n)**, one **Open** on every row, and
  only Left open counts in Needs you. Hours: **Not finished yet** (Running now,
  Not running now).
- After the next nightly run: a client with a stranded session may show an
  earlier last visit and a slightly slower pace; a client whose first Journey
  session came from Log past session shows a lower, correct #N, and Account
  shows the arithmetic beside Confirm.

**Administrators** (everything above, and)
- Admins → Home's "Sessions left open" goes to **that studio's Today** and
  switches only this iPad ("This iPad is on Solon now.").
- Admins → Machinery → Limbo may show rows with a **staff** badge: a Mindbody
  staff update Journey couldn't place on one trainer at that site, with a
  sentence saying whose number it is and what to do. A trainer who works on
  both Mindbody sites, or whose studios aren't linked to Mindbody, stops
  getting name, email and photo updates from Mindbody unless the update
  carries the name Journey has for them.
- Admins can Arrange any studio's floor; a model's size is theirs (the seed
  writes the twenty Imagine Strength models).

**Demo Mode.** Everything above works there with no second path. Every
trainer leads Demo Mode, so every trainer can Arrange its floor, and its editor
has **Start from the practice layout**. Demo Mode has no Mindbody link, so the
webhook change never reaches it.

**Nothing contacts anyone.** No Mindbody call is added, no timer, no
cadence change; the only bell is the existing one when someone reports a
problem with a machine.

## 4. The restore point and the undo

**Restore point:** `restore/2026-10-12-before-oct12-release` = `5a0bf7ea`,
master before the release (also the live app and the live rules today). The
live Cloud Functions are `3735f38e`'s, unchanged on master since, so the same
tag restores the webhook.

- **The app** (the web service and the crons): on Render, the web service's
  Events → the last good deploy → Rollback, and the same on each cron's Builds.
  Or `git push --force origin restore/2026-10-12-before-oct12-release:master`
  and Render's three presses. Ask Claude first.
- **The rules can stay after the app goes back.** The old app never writes the
  finish marker or `floorPlans`, and nothing it does in normal use is refused
  (step 5). **What can't be done is the other way round:** never put the old
  rules back while the new app is live. The new app's Finish needs the marker
  path (an offline Finish replayed after a reload would be refused with nothing
  left to catch it, and the session would stay open) and its map needs
  `floorPlans`. If the rules themselves must go back: the app first, wait for
  the iPads to load it on the Hub, then the rules from a worktree at the tag
  (`docs/ops/DEPLOYS-AND-ROLLBACK.md`, "The rules").
- **The indexes:** no undo. An extra index costs a little on each write.
- **The function:** from the project folder,
  `git worktree add ..\journey-restore-oct12 restore/2026-10-12-before-oct12-release`,
  junction `node_modules` and `functions\node_modules` into it
  (`cmd /c mklink /J ...`), then in it
  `npx firebase deploy --only functions:mindbodyWebhook --project prod`. Golive
  prints the exact lines and keeps them in its log. Limbo rows written
  meanwhile stay; dismiss them. Afterwards master still has the fix, and the
  next functions deploy would put it back: tell Claude.
- **The seed:** the same command with `--remove` (a dry run), then `--remove
  --commit`. It removes only the twenty still signed by the seed and refuses
  any a studio's machine still names.
- **Data:** nothing stored changes shape. Finish markers, layouts and sizes
  stay and are harmless to the old app; cleaning marks made with the new app
  are the same `machineCare` fields the old care sheet writes.

   Admins → Machinery → Mindbody sync: every studio healthy.
7. Firebase console → Functions → `mindbodyWebhook` → Logs: no errors on the

   a linked trainer: their name is on the Hub within a minute. Never make a

   → Indexes): `sessions (hostedAtStudioId, status, createdAt)` and `trainers
   (mindbodyStaffId, accessibleStudioIds)`. The script's read-only check reads
   the first; the second (an array-contains index) only the console shows.
